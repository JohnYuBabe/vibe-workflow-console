# 0002. 完成后定格，用行锁挡住并发写

状态：已采纳（2026-10-19 修订）
日期：2026-10-19

## 背景

完成门禁只在 `review → done` 的瞬间判定。如果任务进入 done 之后还能改规格、删验收、删验证或删会话，任务会停在 done，却不再满足任何一道门禁。历史记录看起来是完成的，证据却已经不存在。

同时，这些写入口和流转可能并发：一个请求在检查「任务是否 done」，另一个请求正在把它流转到 done。检查与写入之间必须互斥。

## 决策

done 任务拒绝以下操作，统一返回 409 `TASK_IMMUTABLE`：

- 修改标题、规格、人工记录。
- 修改验收标准。
- 新增或删除验证记录。
- 新增或删除 AI 会话。
- 删除任务本身。

实现放在 `assertTaskMutable`（`apps/server/src/tasks/assert-task-mutable.util.ts`）：在事务内执行 `SELECT status FROM tasks WHERE id = ? FOR UPDATE`，拿到任务行的写锁后再判断状态。调用方必须在事务中使用。任务更新、验收标准重写、任务删除、验证增删、会话增删都复用同一个函数，不再各自写一遍状态判断。

复用的写入口：

- `TasksService.update`、`replaceCriteria`、`remove`。
- `VerificationsService.create`、`remove`。
- `AiSessionsService.create`、`remove`。

## 考虑过的替代方案

- 完成后仍可补备注或修正证据。允许补记录能让 done 任务保持准确。没选：只要还能删验证或会话，就无法保证 done 仍然达标；「可补不可删」需要为每类记录维护两套权限，复杂度高于收益。
- 软删除。给记录加 `deletedAt`，删除只是隐藏，门禁统计排除已删除项。没选：门禁读的是真实记录，软删除后仍需在所有查询里过滤；任务本身仍可被删除，问题没有真正解决。
- 只靠前端隐藏写入口。done 时页面不渲染编辑、删除按钮。没选：接口仍然可被直接调用，服务端必须自己拦；前端隐藏只能算体验优化，不能当约束。

## 后果

收益：done 一旦成立，规格与证据不会再被改掉；检查与写入在同一事务、同一把行锁下完成，避免「检查完状态、写入前被流转到 done」的竞态。

代价：引入 MySQL 专用的裸 SQL，绕过 Prisma 的类型检查；每个新的任务级写接口都必须记得调用 `assertTaskMutable`，漏掉一个就出现缺口。项目整体删除走 `project.delete` 级联，不调用该检查，done 任务会随项目一起消失，这与「任务本身不可删除」的表述存在口径差。流转事务本身没有对任务行执行 `FOR UPDATE`，只对状态做条件写，两者是否完全互斥缺少代码层面的证明。
