# 0007. 看板复用 GET /tasks，客户端分组

状态：已采纳
日期：2026-10-19

## 背景

看板要按五个状态跨项目展示任务，并支持项目筛选、关键词筛选和 `?status=` 单列深链。如果新增一个看板接口，就要再定义一套筛选、分组和分页口径；同一批任务会同时存在「列表接口」和「看板接口」两种返回结构。

看板是跨项目的全局视图，而 `GET /tasks` 已经支持按项目与状态筛选；再做一个看板接口，等于把同一批数据换一种形状返回。

## 决策

不新增 endpoint，直接复用 `GET /tasks` 的全量任务列表，在客户端分组：

- `BoardView.vue` 一次拉 `GET /tasks`，按 `TASK_STATUSES` 分成五列。
- 路由是 `/board`，五列固定为 `draft / ready / in_progress / review / done`。
- 项目筛选、关键词筛选、`?status=` 单列都在客户端完成。
- 单列模式只渲染一个状态，并提供「查看全部」返回完整看板；非法状态按未筛选处理。
- 同时拉 `GET /projects`，用于项目筛选和任务缺少项目信息时的名称回退。
- 任务摘要自带 `project` 字段，卡片优先直接用；项目列表只作为回退。
- 列内按 `updatedAt` 倒序，时间相同按 `id` 倒序；`?projectId=` 指向不存在的项目时回退到全部项目。

服务端 `GET /tasks` 只接受 `projectId` 与 `status` 两个筛选参数，不提供 `take` / `skip`。

## 考虑过的替代方案

- 服务端分组接口。新增 `GET /board`，直接返回五列。没选：会多一套筛选与分组口径，前端仍要处理单列深链和项目名回退；当前任务量下收益不足以抵消重复。
- 服务端分页。给 `GET /tasks` 加 `take` / `skip`，看板按列分页。没选：看板需要跨状态展示，分页后每列的数量和排序都要重新定义；当前没有容量压力，过早分页会让接口和前端都变复杂。
- 数据库聚合。用 `groupBy` 在数据库里算每列数量。没选：看板需要卡片内容，不只是计数；聚合只能给出数量，仍要再查一次任务。

## 后果

收益：没有新增接口，筛选与分组只有前端一份实现；`?status=` 单列、项目筛选、关键词筛选可以自由组合；服务端任务列表保持简单。

前端一次拿全量任务，首屏时间随任务总数增长；数据量小时这不是问题，数据量变大后需要重新评估。

代价：`GET /tasks` 没有 `take` / `skip`，任务增长后一次拉全量；筛选逻辑只在 web 端，无法复用给其他客户端；数量超过文档假设的「几百条」时需要重做接口。这个容量前提只有 `docs/day4.md` 的文字说明，仓库里没有性能测试或容量基准，无法验证。
