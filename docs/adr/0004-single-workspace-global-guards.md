# 0004. 单工作区加全局 JWT/权限守卫

状态：已采纳
日期：2026-10-19

## 背景

系统需要区分只读与可写：`viewer` 不能创建、修改、删除，`editor` / `admin` 可以。如果把权限判断散落在每个 controller，新增接口时很容易漏掉；如果做成多租户或项目级授权，又要改所有列表与详情查询。

这是一个个人作品项目，当前只有一个工作区，所有登录用户看到同一批 demo 数据。

如果做成多租户，项目、任务、决策、看板与仪表盘的查询都要带租户条件；如果只按角色判断，又无法表达「谁能看哪个项目」。当前取舍是先解决角色，不解决归属。

## 决策

用两个全局 `APP_GUARD`，按顺序执行：

1. `JwtAuthGuard` 解析 token，把用户放进 `request.user`。`@Public()` 只放行登录与健康检查。
2. `PermissionsGuard` 读取 `@RequirePermission('resource:action')` 声明的权限，检查用户是否全部具备；未声明权限的路由只要求登录。

角色与权限在 seed 中预置：`viewer` 只带读权限，`editor` / `admin` 带写权限。守卫只认权限字符串，不认角色名。

数据层不做项目归属校验。`GET /projects` 与项目详情只按 id 查询，不按 `ownerId` 过滤；所有登录用户共享一个工作区。`Project.ownerId` 只记录创建者，不参与授权。

## 考虑过的替代方案

- 多租户。每个用户或团队一个工作区，所有查询带租户条件。没选：当前没有多租户需求，引入后要让项目、任务、决策、看板、仪表盘的每个查询都带租户过滤，改动面远大于收益。
- 项目 owner 级授权。只有 `ownerId` 能改项目，其他人只能读。没选：demo 场景里 editor 需要协作，按 owner 隔离会让种子数据和演示流程互相打架；而且 `ownerId` 目前只是记录字段，改成授权依据需要补一套转移与共享语义。
- 对象级 ACL。为每个项目维护成员表。没选：这是多租户的简化版，仍然要改全部查询，且当前没有成员管理界面。
- 每个 controller 自挂守卫。没选：新增 controller 时容易漏挂，权限会变成默认放行；全局守卫的默认值是「要求登录」，漏声明权限只会放宽到登录用户，不会完全公开。

## 后果

收益：权限判断集中在一处，新增接口只要声明 `@RequirePermission`；`viewer` 的写操作在服务端被 403 拦下，不依赖前端隐藏按钮；登录与健康检查通过 `@Public()` 显式豁免。

权限检查只发生在 HTTP 路由层，service 之间的内部调用不重复判断。

代价：任何有 `project:read` 的账号能读全部项目，任何有 `project:write` 的账号能改任意项目；`Project.ownerId` 不参与授权。将来加多租户要改所有 list/detail 查询和权限语义，并补迁移。「单工作区」目前只写在架构文档与本 ADR 里，README 与界面都没有声明；如果产品预期按 owner 隔离，这是一个安全缺口。
