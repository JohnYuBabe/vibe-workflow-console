# 0006. 列表只返回摘要，详情才带长正文

状态：已采纳
日期：2026-10-19

## 背景

决策正文可能很长：背景、候选方案、决定、后果四段加起来可能是几千字。列表页只需要知道「有哪些决策、属于哪个项目、关联哪个任务」，任务详情里的决策卡片也只展示标题、状态、所属项目与更新时间。一次把全部正文拉回来，会浪费带宽与内存。

列表页、项目详情的决策卡片、任务详情的关联决策卡片都只展示摘要；只有打开只读弹窗或编辑表单时才需要全文。

如果列表接口带全文，调用方即使只渲染标题，也要为整段正文付出序列化、传输和内存成本。决策数量越多、正文越长，差距越明显。

## 决策

定义两个返回类型（`apps/server/src/decisions/decision.types.ts`）：

- `DecisionSummary`：`id`、`projectId`、`taskId`、`title`、`status`、项目/任务/创建者的最小引用、时间。
- `DecisionView`：在摘要基础上附带 `context`、`options`、`decision`、`consequences` 全文。
- 列表查询不读取正文列；四段正文只出现在详情与写接口（创建、更新）的响应里。

列表查询用 `decisionSummarySelect`，只选摘要字段，正文列不参与查询。详情、创建、更新用完整 `include` 返回正文。

列表默认 100 条，`limit` 上限 200（`ListDecisionsQueryDto`）。前端 `apps/web/src/api/decisions.ts` 用 `DecisionDetail extends DecisionSummary` 表达同样的区分，编辑或只读弹窗先按 id 拉详情。

创建、更新与详情返回同一套 `DecisionView`，调用方不需要区分「刚写完」与「再读一次」。摘要中保留 `project` 与 `task` 的最小引用，列表不依赖额外请求拼名称。

## 考虑过的替代方案

- 列表直接返回全文。接口统一，前端不用二次请求。没选：正文体积不可控，列表页和任务详情卡片都用不到全文；随着决策数量增长，一次列表会把大量长文本放进内存和响应体。
- 前端按需截断。后端仍返回全文，前端只显示前 N 字。没选：带宽和内存已经花掉了，截断只解决视觉问题，不解决传输问题；而且列表接口会随着正文变长持续变慢。
- 为列表增加正文搜索。既然要搜索，就把全文带上。没选：当前没有正文搜索需求；如果将来要做，应该在数据库侧做匹配，而不是把全文拉到前端过滤。

## 后果

收益：列表响应只包含短字段，决策数量和正文长度增长时列表成本基本不变；前后端类型明确区分，调用方不会误以为列表项带正文。

代价：编辑或查看全文前必须再按 id 发一次 `GET /decisions/:id`，多一次往返；前后端各有一套摘要/详情类型，字段变更要同步两处；列表无法直接做正文搜索或摘要预览。创建与更新的响应也带全文，写操作返回体积由正文长度决定；调用方如果只关心 id，仍要接收完整记录。
