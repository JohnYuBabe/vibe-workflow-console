# 0003. 流转用事务加条件写，状态本身当并发令牌

状态：已采纳
日期：2026-10-19

## 背景

两个请求可能同时基于 `review` 通过门禁：一个写 `review → done`，一个写 `review → in_progress`。两次判断都读到了旧的 `review` 状态，如果都直接写入，就会产生矛盾的历史，后写的结果覆盖先写，但两条流转记录都在。

只做事务不够：事务保证原子性，不保证「读到之后、写入之前状态没变」。

如果只在写入前再查一次状态，两个请求仍可能同时读到 `review`，再同时写入。

## 决策

把流转的读取、判定、写入放进同一个 `$transaction`：

1. 读取任务、验收标准、验证结果与会话条数。
2. 调用 `evaluateTransition` 判断门禁。
3. 执行 `updateMany({ where: { id, status: from }, data: { status: to } })`，把状态本身当作并发令牌。
4. `count === 0` 说明状态已被其他请求改掉，抛 409，本次流转作废。
5. 只有 `count === 1` 才写一条 `taskTransition` 记录。

任务、验证、AI 会话与决策的删除沿用同一语义：用 `deleteMany` 后按 `count === 0` 返回 404，避免并发删除时 Prisma `P2025` 变成 500。项目删除是例外：先 `ensureExists` 再 `delete`，并发删除仍可能抛 `P2025`。

实现位于 `apps/server/src/tasks/task-status.service.ts`。事务使用 Prisma 的回调形式，读取、判定、条件写与流转记录在同一次事务中完成；任一步失败都会回滚。

## 考虑过的替代方案

- 单独的 `version` 列。每次写入 `version + 1`，条件写 `where version = ?`。没选：状态列已经能表达「当前处于哪个阶段」，再引入版本列会让每次流转多写一个字段，并为所有写入口增加版本传递。
- 客户端重试。冲突时让客户端自动重发。没选：门禁可能已经变化，重发相当于用旧意图猜新状态；冲突方需要先看到新状态再决定，不能由服务端静默重试。
- 整行悲观锁。事务一开始就 `SELECT ... FOR UPDATE` 锁住任务。没选：会把所有读也串行化，且需要额外的锁等待与超时处理；条件写已经能覆盖流转冲突。
- 允许后写覆盖先写。不做并发判断，最后一条写入生效。没选：会留下两条都声称成功的流转记录，历史无法解释。

## 后果

收益：同一任务的状态流转串行化，冲突方收到 409，不会出现两条矛盾历史；任务、验证、AI 会话与决策的删除也统一用 `count` 判定 404，避免 P2025 泄漏成 500（项目删除尚未统一，见上）。

代价：并发失败方只能拿到 409 后刷新重试；事务内多次查询，持有时间比单条更新长；状态字段同时承担业务状态和并发令牌两种职责。失败响应与真实门禁失败共用 `INVALID_TRANSITION` 附近的分支，调用方需要看 `code` 区分。现状不对任务行加 `FOR UPDATE`，只做条件写，因此「读取门禁后、写入 done 前证据被并发删除」的窗口在代码里找不到互斥依据，现有测试也没有覆盖这个交错。
