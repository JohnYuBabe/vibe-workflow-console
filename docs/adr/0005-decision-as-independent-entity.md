# 0005. 决策独立建模，删除语义按保留历史设计

状态：已采纳
日期：2026-10-19

## 背景

决策要回答「当时有哪些选项、为什么选这个、代价是什么」。它可能先于任务存在，可能跨任务存在，也可能在任务关闭后仍需保留。把决策写成任务备注，会随任务关闭而消失，也无法被单独检索。

决策与任务的关系不是强绑定：一个决策可以只属于项目，也可以关联一个任务。

项目删除是唯一会连带删除决策的路径；其余删除只解除关联，正文保留。

## 决策

建立独立的 `Decision` 模型（`apps/server/prisma/schema.prisma`）：

- `projectId` 必填；`taskId` 可选，最多关联同项目的一个任务。
- 正文拆成 `context`、`options`、`decision`、`consequences` 四段，而不是一段自由文本。
- 状态三态：`proposed`、`accepted`、`superseded`。
- 删除项目时 `onDelete: Cascade`，决策随项目一起删除。
- 删除任务或用户时 `onDelete: SetNull`，保留决策正文与关联历史。

服务端在写入时校验 `taskId` 属于同一项目，跨项目返回 400；空串与纯空白在 DTO 与 service 两处都归一为 `null`，不会以 `''` 进入 Prisma。

创建与更新都经过 `ensureTaskInProject` 校验；`normalizeTaskId` 负责把空串与纯空白转成 `null`，DTO 层也会先做一次归一。

## 考虑过的替代方案

- 把决策写成任务备注。复用任务的人工记录字段，不建新表。没选：决策会随任务关闭而失去落点，也无法跨任务引用；备注是一段文本，拆不出背景、选项、决定与后果。
- 一个决策关联多个任务。用中间表表达多对多。没选：当前的需求是「这个决定影响了哪个任务」，单值足够；多对多会让列表、筛选和删除语义都变复杂，而收益没有场景支撑。
- 删除任务时级联删决策。保持任务与决策同生共死。没选：决策的价值在于保留「为什么」，任务删掉后决策仍应可查；`SetNull` 保留了正文，只丢失关联。

## 后果

收益：决策可以独立于任务存在和检索；删除任务或用户不会带走历史正文；四段式正文让「选项」和「代价」有固定位置，不用从一段话里猜。

代价：写入要额外校验任务属于同一项目，跨项目返回 400；空 `taskId` 与纯空白要在 DTO 和 service 两处归一为 `null`；`taskId` 是单值，跨任务共用的决策只能复制或只挂一个任务。`superseded` 只是状态，没有指向替代决策的字段，无法表达「被哪条决策取代」的链路。
